# ドラッグ＆ドロップの操作と検証

- 一覧・ギャラリーのドラッグ元は45%の不透明度で表示し、選択の青い背景を外す。
- 保存先にできるフォルダー、サイドバー、パンくずだけをホバー時に強調。一覧背景にもドロップできるが、パネル全体は着色しない。
- 自分自身、子孫、同じ親フォルダーへのドロップは表示済みパスで除外し、実パスによる最終検証は転送ワーカーで行う。
- Skylis内のドラッグでは、離した時点のCtrlはコピー、Shiftは移動。無指定なら項目ごとに同じボリュームは移動、異なる／識別不能なボリュームはコピー。
- 外部プロセスからSkylisへのドロップはコピー専用。Shiftを押しても元ファイルは残す。
- ボリューム判定は単一の転送ワーカー上で行う。Windowsは実ボリュームGUID、UNCは共有ルートを使い、macOSはデバイスIDを使う。ドライブ文字だけでマウント先を推測しない。
- 既存のWindows IFileOperationによる競合・進捗・取り消しUIを維持。コピー／切り取りのクリップボード指定は既定ドロップ動作と独立。
- Native dragのキャンセル／終了時は元ウィンドウを再描画し、半透明状態を解除する。フィードバックはペイロードを弱参照する。

## ネイティブ連携の制約

GPUI coreのネイティブドロップ変換では、キーイベントが届かないOLEループでも、Enter／Pending／Submit時点のOS修飾キー状態を取得する。

外部アプリからSkylisへの受信では、gpui-fast-windows 0.1.15のOLE実装が`DragEnter`・`DragOver`・`Drop`で`DROPEFFECT_COPY`を固定返却する。Skylis側の実操作もコピーに統一したため、外部入力で表示と実操作が食い違って元ファイルを移動することはない。

現在の`FileDropEvent`は外部の送信元が許可したeffect、元の`IDataObject`、操作完了通知を扱わない。外部入力を移動に拡張する場合は、それらの伝達と送信元との削除責任を整理する必要がある。送信元がコピーを許可しない形式や仮想ファイルのドロップには対応しない。

同じSkylisプロセスから始まったnative dragは`NATIVE_DRAG_ACTIVE`で区別し、窓の外へ出してから戻す操作や同一プロセスの複数ウィンドウ間では通常の自動／修飾キー判定を保つ。この経路もOSカーソルはCOPY印のため、内部移動時の印には制約が残る。別プロセスのSkylisから来たドロップは外部入力としてコピーする。

圧縮ファイル内は読み取り専用。メンバーを通常のファイルパスとしてドラッグ／受信せず、解凍後に操作する。

Skylisから外部アプリへの送信は別経路で、独自ブリッジが`SHDoDragDrop(COPY | MOVE)`を呼ぶ。受け取ったOS／アプリが操作を決定・実行し、Skylisは結果を受けて一覧を更新する。

## 自動検証

`cargo test -p explorer --locked file_operations::` と `cargo test -p explorer --locked folder::transfers::` で、実ローカルボリューム、混在ボリューム・UNC識別、修飾キー優先、ネイティブドロップ時のキー変更、無効対象、完了／取消後のフィードバック解放を検証する。

実ドライブ間の移動、外部アプリとのカーソル表示、macOS実機は別途実機確認が必要。
