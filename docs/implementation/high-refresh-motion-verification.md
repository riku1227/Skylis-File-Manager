# 高リフレッシュ・スクロール実装の検証

2026-11-15。設計レビューはOpus 5.5、実装後は別エージェントの全体レビューを実施。未解決の重大なコード指摘なし。Windowsで実装と実機動作を確認したが、安定120fpsや全ディスプレイ構成の対応を保証する結果ではない。

## 実装

- `d00488b`: GPUI Fast **=0.1.15** coreのみvendor化。実行時のウィンドウ別描画上限、既存電力制限との合成、遅延した描画要求の保持。上限なしは従来のネイティブ描画供給を維持する。
- `866e08a`: 高リフレッシュと滑らかなスクロールの独立した永続設定、画面Hz表示、OSのモーション低減を優先するアダプター、一覧/ギャラリーの補間と端スクロール。
- 上限は通常のon-screen presentに適用。OS必須presentは例外、入力の整合性を保つ同期CPU drawは対象外。オフは「最大60」であり一定60fpsの保証ではない。
- 補間は100ms以内の時間ベースHermite。Windowsの行数設定で正規化できる低頻度のノッチ入力だけに適用し、端数・高頻度・精密入力は既存の直接処理へ戻す。
- クリック時は最後に描画したオフセットへ凍結。ナビゲーション・タブ移動・レイアウト変更・プレビュー・非表示で古い動きを停止する。ファイルを開く処理をアニメーション待ちにしない。

## Windows release実測

実行ファイルSHA-256:
`2402AE6C7012302A6C38E2454B60E4CF9EB185D9C4D9C5627C141A95A7A5FB21`

RTX 3080、ウィンドウ画像は約1280×800、同じ1500個の小さなtxtファイル、標準密度、ダークテーマ、インスペクター表示。自動サイズ計算を無効にした隔離APPDATAで計測し、本人の設定を変更していない。画面APIがこのウィンドウについて返した値は約160Hz。一方、CIMの簡易GPU照会は3840×2160/119Hzなので、CIM値をそのままウィンドウの画面情報として使わない。

[Intel PresentMon 2.6.0](https://github.com/GameTechDev/PresentMon/releases/tag/v2.6.0)を公式配布から利用。PIDで対象を限定、独立したセッションで28秒記録。通常権限で対象のDXGIイベントを取得できた。表示モードは`Composed: Flip`。昇格なしでは他ユーザー・短命プロセスの照会が制限される旨の警告は出るが、このPIDは識別されている。

同じ位置へ自動操作ツールの`pixels:120`指定でスクロールを240回、待機を挟まず送信。オン14.842秒、オフ13.075秒の入力列になった。最初のpresentから500msを除き、続く10秒の区間内のサンプルを集計した（最初と最後のサンプル間は約9.98秒）。これはUI自動操作を含む実動作測定で、制御されたGPUベンチマークや特定の物理ホイール機種の測定ではない。

| 指標 | 高リフレッシュ: オン | オフ（最大60） |
| --- | ---: | ---: |
| DXGI present頻度 | 97.85 /秒 | 44.06 /秒 |
| PresentMonが表示完了を観測した頻度 | 88.49 /秒 | 44.06 /秒 |
| present間隔 p50 / p95 / p99 | 11.15 / 15.58 / 26.69ms | 18.54 / 37.35 / 40.31ms |
| 表示間隔 p50 / p95 / p99 | 9.90 / 18.54 / 31.55ms | 18.75 / 39.42 / 39.53ms |
| 設定時間予算 | 6.25ms（取得160Hz） | 16.67ms |
| 予算より長いpresent間隔 | 759 / 977 | 365 / 440 |
| CPU時間 / 約10秒 | 5.672秒 / 9.954秒 | 2.141秒 / 10.063秒 |
| CPU使用量（1論理コアを100%換算） | 57.0% | 21.3% |

表示頻度は`TimeInMs + MsUntilDisplayed`の有効サンプルから算出。present回数、描画callback回数、実表示を混同しない。CPUはプロセス全スレッドの累積時間を約100msごとに採取したもの。CPU値はPC全体の使用率や電力ではない。時間予算超過はフレーム間隔の比較であり、CPU描画処理がその時間を消費したという意味ではない。

オンでは60を超える表示を確認。オフでは60以下を確認した一方、一定60には達していない。160Hzの画面への追従設定でも、現在の実動作は安定120fpsを満たしていない。描画供給、Windows共有DWM待機、入力・他アプリ負荷を分離した追加プロファイルが必要であり、原因をこの測定だけで断定しない。

操作終了後、オン・オフ各12秒の独立した記録は正常終了し、presentイベントなし（PresentMonはCSVを生成しない）。CPU消費はオン0.0625秒、オフ0秒。静止中にアニメーションの描画ループが続いていないことを確認した。

## 実画面確認と未検証範囲

設定のオン/オフ表示と独立切替、保存・再起動後の復元、一覧の連続ホイール、ギャラリーへの切替・スクロール・クリック選択、Home/End、タブ追加/閉鎖、親フォルダー移動と戻る操作を最終releaseで確認した。設定UIの取得HzはFPSとは区別して表示する。

- `MsAllInputToPhotonLatency` / `MsClickToPhotonLatency`は今回の記録でNA。入力から最初の可視描画までの遅延を測れたとは扱わない。オフでは上限待ちと次のnative frame機会までの待ちが加わり得る。
- OS低減設定のライブ変更、PTP/非PTP/フリースピン機種別、VRR有効/無効、混在Hzでの画面移動、macOS実機は未検証。コードの能力取得失敗はunknownとして扱う。未検証を「非対応」とは表示しない。
- Windows共有DWM供給のバックエンドは変更していない。この環境の160Hz表示とCIM119Hzだけでは、混在Hzが原因と再現確認したことにはならない。
- 画像ギャラリーのdecode/cache条件を揃えた性能比較は未実施。今回の性能測定はtxt一覧。画像メモリ・worker上限は既存機構を維持する。
