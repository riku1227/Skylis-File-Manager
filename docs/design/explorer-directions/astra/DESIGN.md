# 3方向の設計メモ

共通の架空フォルダー「灯台プロジェクト」を扱う、日本語のローカル完結HTML試作。
主役は詳細ファイルリスト。脇役は現在地・検索・選択項目の詳細。
レビュー説明はこのメモに集約し、アプリ本体に混ぜない。
追加質問・再委任・既存コード変更は行わない。

1. 透庭: panel / rail / 明るいミントと杏色。Split、右に文書プレビュー。
   白い作業面の外側に薄い色を残し、ナビゲーションだけ軽く浮かせる。
2. 紙面: editorial / topbar / アイボリーとインク。上下のSplit。
   サイドバーを廃し、横方向の場所ナビと下部インスペクターで横幅をファイルへ返す。
3. 対座: panel / topbar / 深いプラム。Columns、左右に詳細リスト。
   移動元・移動先を同時に見渡す構造。詳細は下部の細い文脈帯に集約。

共通サンプル12項目、検索・単一選択・密度・詳細開閉・テーマ切替を実装。
アイコンは自作カラーSVGの仮素材。OS取得アイコンではない。本番はOSのカラーアイコンを保持する。
操作アイコンは24px座標・1.7px線の統一SVG。
1280×800と1100×700で検証。GPUI Fastの再現や速度をHTMLから保証しない。

## 比較のポイント

| 案 | 狙いと構造 | 選択と奥行き | 適する使い方 / 代償 |
|---|---|---|---|
| 1 透庭 | 常用の一覧を明るく軽やかに。左の薄い色面にナビ、白い面に一覧、右にプレビュー | 淡緑の選択＋細い左線。背景の杏・ミントがナビ越しに見える。ファイル面は不透明 | 文書を見ながら探す。縦方向の余裕を使うので小画面ではスクロールが増える |
| 2 紙面 | 左ナビを撤去。場所を横並びにし、メタデータを下に集約。幅を名前と列に渡す | 選択は端から端まで続く細い帯。枠と影を減らした紙面の連続性 | 長い名前・多数の列を比較。常設のフォルダーツリーを必要とする人には不向き |
| 3 対座 | 左に作業フォルダー、右に書き出し先を常設。下に選択情報 | 二つのリストの面差、プラムの選択、境界線で作業対象を示す | 参照元と成果物を往復。単一フォルダーだけを扱う場合は幅の効率が下がる |

以前の案の評価原因を断定していない。「今風」を、装飾の追加だけでなく操作と内容の階層、面の連続性、作業領域の使い方を見直す余地として解釈した。3案は配色プリセットではなく、右詳細・下詳細・二面という別の判断を比較するもの。

## 操作とサンプル

- 全案の主リストは同一の12項目・サイズ・日時。対座の右側はこのうち3ファイルを書き出した架空コピー。
- 入力検索（NFKC正規化、大文字小文字無視）、Ctrl/Cmd+Fで検索へ、Escapeで解除。
- クリックで単一選択と詳細更新。主リストは上下キーで選択、Enter/Spaceにも対応。
- 既定順/逆順の反転、コンパクト表示、詳細ペイン開閉、ライト/ダーク。
- 対座の右側ファイルもクリック/Enterで詳細表示。検索は左の作業フォルダーを対象とする。
- 文書表紙は埋込みの自作SVG。PDF読込は行わない。他の項目は種別アイコンとメタデータを表示。

未実装: 実ファイルI/O、コピー・移動・削除、フォルダー遷移、タブ、複数選択、列幅変更、名称による本物のソート。場所ナビとOSウィンドウボタンは静的な構造表現で、押せるボタンとして偽装しない。代表操作の視覚試作であり製品の機能完成版ではない。

## GPUI Fastへの実装注意

1. **透庭**: HTMLは静的なradial-gradientと半透明の単色面のみ。backdrop-filter、屈折、OSのMica/Vibrancy APIは使っていない。GPUIでグラデーションが適切に扱えない場合、ウィンドウ寸法ごとのキャッシュ画像または単色の淡い色面で代替。背景を毎フレーム再生成しない。影も必要なら一段の細い枠へ置換する。
2. **紙面**: 平面塗りと線で構成。下部詳細は固定高さを先に確保して一覧の残余高さを計算する。長いファイル名と日本語フォントの実測、DPI変更時の列幅、詳細の非表示時のスクロール位置を検証。
3. **対座**: 左右別の選択・フォーカス・スクロール状態を持つ設計が必要。HTMLの最小実装から本番へ移す際は、操作対象ペインを状態モデルに持たせる。二面とも仮想化し、片側変更で他方の全行を再描画しない。上部linear-gradientは単色プラムで代替可能。
4. 共通: OSカラーアイコンは非同期取得＋DPI/種類/パス別キャッシュ。UI色に合わせた減色をしない。プレビュー読込も別処理にし、選択変更時はキャンセルする。統一操作SVGは必要分だけ静的アセット化。
5. 性能検証: 1万/10万件の列挙、連続キー選択、検索中の再描画、両ペイン同時スクロール、100/150/200% DPI、リサイズ、低性能GPUでのフレーム時間・VRAM・CPUを計測。16.7msを仮の比較目安とするが達成保証ではない。
6. ウィンドウ上部は見た目だけのカスタムchrome。Windowsのドラッグ領域、スナップ、ヒットテスト、アクセシビリティは別途実装検証する。macOSでもOS固有の閉じる等を適切に提供しつつ、本文の共通外観を維持する。

参考: [Appleの2025年6月デザイン発表](https://www.apple.com/newsroom/2025/06/apple-introduces-a-delightful-and-elegant-new-software-design/)の、操作層を内容から分ける考え方を参照。Appleの動的な反射・屈折を再現したものではない。

## 検証と撮影

Windowsのインストール済みChromeをPlaywrightからheadlessで起動し、file://で読込。サーバー・preview_*・外部ネットワークは使用しない。`node build.cjs` で再生成、`node verify.cjs` で検証（Playwright参照先はこの環境の絶対パス）。

- 全案: 初期12行、検索一致1行、0件表示、Escapeで12行へ復帰、行クリックで詳細一致、詳細開閉、コンパクト状態、順序反転、テーマ切替を自動確認。
- 1100×700でページと一覧に横オーバーフローなし。縦はリスト内スクロールを使用。
- ページJavaScriptエラー0、HTTP等の外部リクエスト0。詳細は `verification.json`。
- 各案1280×800の既定テーマ・逆テーマ、1100×700の既定テーマをPNG保存。
- 目視後、透庭の標準行高を42→40px、紙面の見出しと詳細帯を縮小し、1280×800で12項目が見える構成へ修正。対座も行高と見出しを縮めた。
- 詳細非表示指定が案別CSSに上書きされる不具合を修正後、全案の操作検証と撮影を再実行。
